# AI Sandbox Agent

A versioned autonomous coding-agent framework that executes AI-generated tasks inside isolated Docker sandboxes.

The project evolved through three major versions:

* **V1** — Basic autonomous shell-command agent
* **V2** — Fixed `/sandbox` workspace with persistent artifact collection and task tracing
* **V3** — Tool-based agent architecture with a dedicated Tool Registry

The current production version is **V3**.

---

# 1. Overview

AI Sandbox Agent allows a user to provide a natural-language task such as:

```text
Create hello.py that prints "Hello from Sandbox".
Run it, verify the output, and confirm the file exists.
```

The agent then:

1. Creates an isolated Docker sandbox.
2. Creates `/sandbox` as the working directory.
3. Sends the task to the LLM.
4. Determines the next action.
5. Executes the action inside the sandbox.
6. Sends the result back to the LLM.
7. Continues until the task is verified.
8. Collects generated files.
9. Stores artifacts permanently on the host.
10. Generates an artifact manifest.
11. Stores structured and human-readable logs.
12. Destroys the temporary Docker container.

The important design principle is:

```text
LLM
 ↓
Agent
 ↓
Sandbox / Tool Registry
 ↓
Docker Container
 ↓
Execution
 ↓
Observation
 ↓
LLM
```

The Docker container is temporary.

The generated artifacts and logs are persistent.

# 3. Version History

## V1 — Basic Autonomous Agent

V1 introduced the basic autonomous execution loop.

```text
User Prompt
    ↓
LLM
    ↓
Shell Command
    ↓
Docker Sandbox
    ↓
Command Output
    ↓
LLM
    ↓
Next Command
```

The LLM generated shell commands directly.

Example:

```text
printf '%s\n' 'print("Hello from Sandbox")' > hello.py &&
python3 hello.py &&
test -f hello.py
```

### V1 characteristics

* Docker sandbox
* `/sandbox` workspace
* Autonomous execution
* Shell commands generated by the LLM
* Command output returned to the LLM
* Maximum-step protection
* Basic logging
* Temporary sandbox lifecycle

### V1 limitation

Generated files existed only inside the temporary container.

When the container was destroyed, the files were lost.

---

# 4. V2 — Persistent Workspace and Artifacts

V2 fixed the workspace lifecycle and introduced persistent artifact collection.

The sandbox always uses:

```text
/sandbox
```

The host repository contains:

```text
artifacts/
```

After successful execution, files are copied from the container into:

```text
artifacts/<task-id>/
```

Example:

```text
artifacts/
└── task-734fdf8e98d2/
    ├── hello.py
    └── manifest.json
```

The manifest records:

* Task ID
* Container ID
* Workspace
* Artifact directory
* Artifact count
* Original sandbox path
* Relative path
* Host path
* File type

Example:

```json
{
  "task_id": "task-734fdf8e98d2",
  "container": "agent-sandbox-b41c2f83",
  "workspace": "/sandbox",
  "count": 1,
  "artifacts": [
    {
      "path": "/sandbox/hello.py",
      "relative_path": "hello.py",
      "host_path": "/home/ec2-user/sandbox-ai/artifacts/task-734fdf8e98d2/hello.py",
      "type": "python"
    }
  ]
}
```

# 5. V3 — Tool-Based Agent

V3 changes the interaction model.

Instead of asking the LLM to generate arbitrary shell commands for normal operations, the LLM selects a registered tool.

Available tools:

```text
filesystem.write
filesystem.read
filesystem.list
python.run
terminal.exec
```

The architecture becomes:

```text
                    ┌─────────────────┐
                    │      User       │
                    └────────┬────────┘
                             │
                             ▼
                    ┌─────────────────┐
                    │      Agent      │
                    └────────┬────────┘
                             │
                             ▼
                    ┌─────────────────┐
                    │       LLM       │
                    └────────┬────────┘
                             │
                       Tool Selection
                             │
                             ▼
                    ┌─────────────────┐
                    │  Tool Registry  │
                    └────────┬────────┘
                             │
          ┌──────────────────┼──────────────────┐
          ▼                  ▼                  ▼
 filesystem.write     filesystem.read     python.run
 filesystem.list      terminal.exec
          │                  │                  │
          └──────────────────┼──────────────────┘
                             ▼
                    ┌─────────────────┐
                    │ Docker Sandbox  │
                    │    /sandbox     │
                    └─────────────────┘
```

# 17. Example V3 Tool Interaction

For a task requiring a Python file, the LLM can generate:

```json

  "tool": "filesystem.write",
  "arguments": {
    "path": "hello.py",
    "content": "print(\"Hello from V3\")\n"
```

Next:

```json
{
  "tool": "python.run",
  "arguments": {
    "path": "hello.py"
  }
}
```

The result is returned:

```text
Hello from V3
```

Then:

```json
{
  "tool": "filesystem.read",
  "arguments": {
    "path": "hello.py"
  }
}
```

The LLM can verify:

```python
print("Hello from V3")
```

Once all requirements are satisfied:

```json
{
  "action": "DONE"
}
```

# 19. Workspace Security

All normal agent files must remain inside:

```text
/sandbox
```

The Tool Registry validates paths before execution.

For example:

```text
hello.py
project/main.py
outputs/result.json
```

are valid.

This must be rejected:

```text
../../etc/passwd
```

The expected security response is:

```text
Path escapes sandbox workspace
```

This prevents filesystem tools from escaping the sandbox workspace.

# 28. Failure Handling

If a tool or command fails, the result is sent back to the LLM.

Example:

```text

RETURN CODE: 1
STDERR: ...
```

The agent can then:

```text
Analyze
   ↓
Fix
   ↓
Execute again
   ↓
Verify
```

The agent should not mark a task as completed merely because a previous command succeeded.


```python

```

not:

```python
from logger import Logger
```

Verify:

```text

```

## Docker Workspace Error

If Docker reports:

```text
chdir to cwd "/sandbox" failed
```

the container is attempting to start with `/sandbox` before the directory exists.

The sandbox manager must create `/sandbox` as part of container initialization before commands execute there.

Verify Docker/container initialization and the current `sandbox_manager.py`.

Check:

# 38. Security Model

The current architecture uses multiple security boundaries.

### Container isolation

Tasks execute inside Docker.

### Workspace restriction

Normal file tools operate within:

```text
/sandbox
```

### Path validation

Path traversal such as:

```text
../../etc/passwd
```

is rejected.

### Step limit

The agent cannot execute unlimited steps.

### Temporary execution environment

The Docker container is destroyed after the task.

### Persistent output separation

Artifacts are copied to the host only through the controlled artifact-collection process.

---

# 39. Important Security Consideration

`terminal.exec` is intentionally powerful.

It should be treated as a privileged sandbox capability rather than an ordinary filesystem operation.

The Docker environment should therefore be configured appropriately for the deployment's threat model.

For production environments, consider additional controls such as:

```text
CPU limits
Memory limits
Process limits
Network restrictions
Filesystem restrictions
Container user restrictions
Execution timeouts
Command allowlists
Resource quotas
Image pinning
Read-only mounts
Secret isolation
```

These are deployment-level hardening measures and should be evaluated before exposing the agent to untrusted users.

```text
Host artifacts/<task-id>/
   ↓
manifest.json
   ↓
Docker Container Destroyed
```

Therefore:

```text
Container = temporary
Artifact = persistent
Log = persistent
Task ID = trace identifier
```

# 41. Why V3 Uses Tools

V2 required the LLM to generate shell commands.

For example:

```text
printf 'print("Hello")\n' > hello.py
```

V3 allows the LLM to express intent:

```json
{
  "tool": "filesystem.write",
  "arguments": {
    "path": "hello.py",
    "content": "print(\"Hello\")"
  }
}
```

The application decides how that operation is implemented.

This creates a cleaner separation:

```text
LLM
=
Decision Maker

Tool Registry
=
Capability Layer

Sandbox Manager
=
Execution Layer

Docker
=
Isolation Layer
```

This architecture is easier to extend and govern.
